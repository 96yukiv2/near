# パスキー認証

Better Auth を Nuxt のサーバーで動かし、Supabase Auth のカスタム OIDC プロバイダーにつなぐ構成です。初回登録に実メールアドレスを必要とせず、Better Auth 内部には配信できない `.invalid` 形式の仮 ID が保存されます。パスキーの秘密鍵は利用者の端末側にあります。

**初期状態では認証・復旧の機能フラグは無効です。** 復旧は Supabase 側セッションの失効を含む検証・対応が完了するまで有効にしないでください。`NUXT_NEAR_AUTH_RECOVERY_ENABLED` はサーバー側、`NUXT_PUBLIC_NEAR_RECOVERY_ENABLED` は画面側のスイッチです。SMTP 情報を設定するだけではサーバーの復旧 API は有効になりません。パスキーフラグが無効の間はログイン準備中の画面を表示します。

## 実装と検証

- パスキー登録後に、実際にパスキーでサインインしたセッションだけが OAuth 認証コードを取得できます。一時ユーザー、登録完了を偽る要求、他人の登録済みパスキーでは取得できないことをテストします。
- OAuth 認証コードの PKCE 検証・再利用拒否、ID トークンの署名・発行元・対象の検証、メール属性が含まれないことをテストします。
- 復旧メールは任意です。登録には最近のパスキーによる再認証と、メールへの確認コードが必要です。利用者が復旧コードを発行して保管し、サーバーはハッシュだけを保存します。復旧時はメールの確認コードと復旧コードの両方を確認して新しいパスキーを登録し、以前のパスキーを無効にします。復旧コードは一度限りで、再発行すると以前のコードは無効になります。復旧後は新しいコードを発行してください。復旧完了時は他の Better Auth セッションを無効にします。既存の Supabase セッションと発行済みアクセストークンの失効は別途対応が必要で、復旧機能を有効にする前に確認します。メール送信は TLS 対応の SMTP 設定がある場合にのみ有効です。
- 削除時は新しいパスキー認証と、Supabase が検証した同一ユーザーのトークンを確認します。Supabase 側の削除後に Better Auth 側を削除し、途中で失敗した場合は本人のパスキー認証で再試行できます。外部サービスを模擬したテストで、他人や未認証の削除拒否と失敗後の再試行を確認します。
- ログインセッションには IP アドレスや User-Agent を保存しません。濫用防止のために別のレート制限情報を DB に保存します。サービスのログ等に接続情報が残る可能性があります。
- DB の `near_auth` スキーマは一般の API ロールから利用できません。サーバーの DB 接続情報と Supabase の秘密キーはサーバーだけに設定し、ブラウザに渡しません。

```sh
npm ci
npx playwright install chromium
npm test
node --test tests/passkey/passkey.node.mjs
```

認証・削除の単体テストと、位置情報を含む API 権限テストは一時的に CI では実行しません。公開前には再び実行し、権限を確認してください。画面の全体確認は Vercel のプレビューなどで行います。Nuxt と PostgreSQL の結合テストが必要な場合は、空のローカル `near_browser_test` DB と `NEAR_TEST_POSTGRES_URL` を用意し、`npm run build` 後に `node --test tests/passkey/nuxt.node.mjs` を実行できます。

## Supabase 用 OIDC クライアントの登録

開発プロジェクト用には [手動登録 SQL](../supabase/manual/register-test-oidc.sql) も用意しています。SQL Editor の結果に一度だけ表示される秘密値を、Supabase のカスタム OIDC プロバイダーに直接入力します。秘密値をチャットやリポジトリに貼らないでください。本番プロジェクトでは使用しません。

認証 DB のマイグレーションとサーバー用接続の準備後、信頼する自分の Supabase プロジェクト用に一度だけ登録します。以下を安全な実行環境の環境変数に設定し、`npm run auth:register-oidc-client` を実行してください。

- `NEAR_AUTH_DATABASE_URL`: 認証 DB の接続文字列。秘密情報です。
- `NEAR_AUTH_DATABASE_CA`: Supabase の Server root certificate。サーバー証明書の検証に使用します。
- `NEAR_OIDC_CLIENT_ID`: Supabase のカスタム OIDC 設定にも指定するクライアント ID。
- `NEAR_OIDC_CLIENT_SECRET`: 同じく Supabase に設定する 32 文字以上の秘密値。秘密情報です。
- `NEAR_SUPABASE_URL`: Supabase プロジェクトの URL（例: `https://<project-ref>.supabase.co`）。

秘密情報をリポジトリにコミットしたり、チャットに貼ったりしないでください。登録されるリダイレクト先は指定した Supabase URL の `/auth/v1/callback` に限定され、秘密値はハッシュ化されます。既存のクライアント ID は上書きしません。Supabase 側では同じ ID と秘密値を設定し、メール属性を任意、PKCE を有効にします。Supabase から Better Auth の issuer にアクセスできる必要があるため、認証保護された Vercel プレビュー URL をそのまま issuer には使えません。

## 有効化前の残作業

1. Supabase Auth にメール省略可能なカスタム OIDC プロバイダーを登録し、Better Auth へ接続する。認証情報を Vercel のサーバー環境に設定し、ログインを実際に検証する。
2. 外部認証後のアカウントで位置 API を直接呼び、未認証、未承認、友達以外、共有停止、友達削除、ブロック、他人の位置更新を検証する。
3. 実際の Supabase とテスト用メール送信先を使い、復旧と両サービスにまたがる削除を確認する。削除中断後の再試行も確認する。
4. 本番、プレビュー、ローカルの WebAuthn RP ID と許可 origin を確認する。Expo での引き継ぎは別途実機で検証する。
5. 認証 DB 用の最小権限ロールと接続方式を用意し、Vercel での IP ヘッダーとレート制限を確認する。IP を含むレート制限データの保持期間も定める。
6. Supabase Auth の従来のメール認証を無効にし、直接 Auth API を呼んでもメール・パスワードで新規登録やログインができないことを確認する。画面を切り替えるだけでは API からの利用を防げない。

認証 DB の接続には `near_auth_server` を用意するマイグレーションを追加しています。このロールはログイン可能ですが、ロール作成・DB 作成・RLS の迂回権限を持たず、`near_auth` スキーマのテーブルに限って読み書きします。パスワードは DB 内でランダムに生成して一時的に Supabase Vault に保存し、Vercel のプレビュー用シークレットへ移した後に Vault の一時コピーを削除する予定です。既存の同名ロールには手を加えず、処理を中止します。開発用 DB にはまだ適用していません。

位置データは現在エンドツーエンド暗号化されていません。パスキー認証を導入しても変わりません。

## 費用

有料プランや自動課金を利用しません。Better Auth 自体は無料ですが、実行基盤・DB・メール送信は個々の無料枠と利用条件が適用されます。Supabase 標準メール送信は一般利用者への復旧メールに使えないため、SMTP を設定する場合は無料枠、送信元ドメイン、課金設定を事前に確認します。無料の範囲で構成できない場合は利用を止め、有料契約に変更しません。
