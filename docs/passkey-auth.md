# パスキー認証の検証

このブランチは認証基盤の検証用です。Near のログイン画面、Supabase Auth、位置共有のアクセス制御にはまだ接続されていません。マージや公開により、メール・パスワード認証がパスキーに置き換わることはありません。

## 検証したこと

- Better Auth の無料のオープンソース版と、一時的な SQLite データベースを使用する。
- Chromium の仮想認証器で、実メールアドレスを使わずにパスキーを登録し、ログアウト後に同じアカウントへログインする。
- 一時アカウントに、実在しない `@anonymous.placeholder.invalid` のメール形式 ID が作られることを確認する。パスキーの秘密鍵はサーバーに送らない。
- テストはメモリ内だけで動作し、実際の Supabase プロジェクトや位置情報には接続しない。

```sh
npm ci
npx playwright install chromium
npm run test:passkey
```

## 実装前に必要な作業

1. Better Auth の OIDC プロバイダーと Supabase Auth のカスタム OAuth/OIDC を接続する。メール属性の送信と保存は最小限にし、登録と再ログインで同じ Supabase のユーザー ID になることをテストする。Supabase の既存テーブルは `auth.users` を参照しているため、外部 JWT を直接渡す方式を使う場合は外部キーや削除処理も見直す。
2. **パスキー登録前の一時アカウントに Supabase のログイン権限を与えない。** 仮セッションのみを使って認証を通過できる実装は不可。認証情報追加・復旧手段の変更には再認証を求める。
3. 既存の API 直接呼び出しテストを、外部認証後のアカウントでも実行する。未認証、未承認、友達以外、共有停止、友達削除、ブロック、他人の位置更新を確認する。
4. 復旧メールは任意かつ事前確認済みのものだけを使う。本人確認、登録・変更・削除、期限付きコードの再利用防止、送信回数制限、メールアドレスの漏出対策をテストする。メール未登録かつパスキーをすべて失った場合、原則として復旧できない。
5. アカウント削除では Supabase 側と Better Auth 側のデータ・セッション・位置情報を整合性を保って削除する。途中失敗時も再試行できる設計とテストが必要。
6. 本番ドメイン、プレビュー、ローカル開発の WebAuthn RP ID と許可する origin を明示する。Vercel のプレビュー URL ごとにパスキーが別になる問題を確認する。Expo での引き継ぎは別途実機で検証する。
7. 認証サーバーの秘密鍵・DB 接続情報はサーバー環境だけで管理し、クライアントには含めない。匿名アカウントの濫用対策と、認証に関するログの取り扱いも確認する。

位置データは現在エンドツーエンド暗号化されていない。パスキー認証の導入だけでは変わらない。

## 費用

有料プランや課金設定を利用しない。Better Auth 自体は無料だが、実行基盤・DB・メール送信は個々の無料枠と利用条件が適用される。特に Supabase の標準メール送信は一般利用者への復旧メールには使えないため、外部メール送信を利用するなら無料枠、送信元ドメインおよび自動課金の有無を事前に確認する。無料枠を超える場合は利用を止め、勝手に有料契約へ変更しない。
